## Updating the site

- **A project changed** (new numbers, new status): read its doc in the career
  repo, then edit `content/projects/<slug>.mjs`. Update `summary`, `figure` and
  `status` as well as the sections, because the home page shows those three.
- **New project**: copy an existing file in `content/projects/`, set a new
  `slug`, `order` and `source`, and write it from the project doc. If it belongs
  under a job on the home page, add the slug to that job's `projects` list in
  `content/site.mjs`. `featured: true` puts it in the main list, `false` in
  "Earlier analytics and smaller builds".
- **CV changed**: update `content/site.mjs` to match `cv/cv.md`, and re-copy the
  PDF into `public/`.
- Then run `npm run build` and look at the result with `npm run dev`
  (http://localhost:4321).

### Content format

Strings are plain text with four inline marks: `` `code` ``, `**bold**`,
`==highlight==` (orange, used once, in the hero headline) and `[label](url)`. A url of `work:<slug>` links to another project page. Raw HTML
is escaped, so do not write tags.

Every project needs these for its home-page card and the top of its page:

- `figure: { value, label }` — the one number shown large.
- `brief: { problem, did, result }` — the three-line version at the top of the
  case study. One or two sentences each, plain language, no jargon a recruiter
  would not know. `result` must state honestly how far the project got.
- `tags: [...]` — which filter chips the project appears under. The keys are
  defined in `work.tags` in `content/site.mjs`; the build fails on an unknown key.
- `status: { kind, label }` — `kind` is `live`, `shipped` (green), `progress`
  (amber) or `demo` (grey outline). The label is free text.
- `chain: [{ i, t, s }, ...]` — the data flow as one row, 3 to 7 steps. `i` is
  an icon, `t` the label (about 16 characters at most), `s` a small second line
  (about 20). It is drawn as the animated diagram at the top of the case study
  and as the row of icons on the home card.

Icons: `i` is the name of a file in `public/icons/` (without `.svg`), or one of
the line glyphs in `GLYPHS` at the top of `build.mjs` (`code`, `queue`, `flow`,
`chip`, `table`, `file`, `phone`, `chart`, `user`, `globe`, `calendar`, `clock`,
`mail`, `check`, `search`, `db`, `wave`, `filter`). To add a logo, drop an SVG
into `public/icons/`.

A project's `sections` is a list of `{ title, blocks }`. A block is one of:

| Block | Renders |
|---|---|
| `'text'` or `{ p: 'text' }` | paragraph |
| `{ h: 'text' }` | sub-heading |
| `{ ul: ['…', '…'] }` | list |
| `{ pre: '…' }` | monospace text diagram (scrolls sideways on phones) |
| `{ table: { head: [...], rows: [[...], ...] } }` | table |
| `{ decisions: [{ title, body }, ...] }` | decision cards |
| `{ evolution: true }` | the version stepper, from the project's `evolution` field |

The stepper under the home-page hero is the `evolution` field of
`content/projects/review-intelligence-pipeline.mjs`. Each version has a
`diagram: { nodes, edges }`. A node is `{ id, c, r, i, t, s, hot }` where `c`
and `r` are its grid column and row. An edge is `[from, to, options]` with
options `both` (arrow at both ends), `dashed` and `hot`. `hot: true` draws in
orange: it marks the part of that design that became the next problem.

## How the home page is laid out

The order is deliberate. It came from studying portfolios that hold attention:
they all say who the person is and what they do before showing any project.
An earlier version went from the intro straight into the flagship project and
Ahmed found it hard to follow. Do not move the deep dive back above the work.

| # | Section | Where its content lives in `content/site.mjs` |
|---|---|---|
| | Hero: headline, intro, buttons, four facts, animated data stream | `hero`, first four rows of `glance` |
| | Moving strip of tool logos | built from `skills` (every item with a logo file) |
| 01 | About: who he is, then the four numbers | `about`, last rows of `glance`, `stats` |
| 02 | What I do: three kinds of work | `pillars` |
| 03 | Selected work: four large rows, then cards, with filter chips | `work` (`spotlight` picks the four rows) |
| 04 | One project in depth: the version stepper | `deepDive` |
| 05 | Problem solving: the "what broke" cards | `stories` |
| 06 | Experience | `experience`, `education`, `certifications`, `languages` |
| 07 | Skills | `skills` (items are `"Name"` or `"Name|icon"`) |
| 08 | Contact | `contact` |

Section headings are two-part: `heading: ['first line', 'second line']`. The
second line is drawn in grey.

A pillar's `tag` is the filter it switches on, `proof` lists three case
studies, `icons` the logos on the card. The project count on each pillar is
worked out from the projects' `tags`.

A project's old `featured` field is no longer read; `work.spotlight` decides
which projects get the large rows.

Every number in `stats`, `stories` and `figure` must appear in the project doc
it comes from. Do not round up or invent one to fill a slot.

## Rules for what the site may say

These come from decisions Ahmed has already made in the career repo. Do not
relax them without him saying so.

1. **Never claim more than the project doc does.** Each project's status label
   says how far it really got, and that is a feature of the site. Specifically:
   - Review pipeline: v1–v4 ran in production. **v5 is deployed but has not run
     a production batch.** Do not describe v5's benefits as achieved, and do not
     quote cost or throughput numbers for it until the doc has them.
   - AI voice setter: a pitch demo against a sandbox CRM. No real customer calls.
   - Keep Tutors phase 2: built and migrated, **not live**. The webhook is built
     but not registered.
   - Merchant pipeline: validation numbers are interim (22,300 checked) until
     the doc says otherwise.
2. **No PySpark, Airflow, dbt, Terraform or Kafka in the skills list** until the
   CV lists them. PySpark was removed from the CV on purpose.
3. **Experience is "over 3 years"**, not four. He is not a graduate yet:
   "expected 2027, Final Year Project II remaining".
4. **Client naming follows the CV, not the project docs.** The docs name every
   client; the public site only names the ones the CV names (IMPRODATA, Keep
   Tutors, Peachtree Partners, JoVE, Lucky Core Industries, Alikhan
   Consultants). The watch brand, the merchant-payments client, the sales client
   and the review product stay unnamed. Leave out internal identifiers too:
   bucket names, database names, client revenue, security-finding details.
5. **Supply chain project**: describe the refund pattern as a gap in policy
   controls. Never as fraud, and never attribute intent.
6. **No phone number on the site.** Email and LinkedIn only. (The CV PDF does
   carry his number; that is his existing choice for the CV.)
7. Aviation and real-estate dashboards: he built the dashboard layer, not the
   platform underneath. Keep the "scope of my contribution" notes.
8. No "open to work" badge and no statement that he is job hunting; he is
   employed. The contact section may invite conversations about roles and
   contract work, which is as far as it goes.

Writing style: first person, plain, specific. The project docs already have the
voice; condense them, do not embellish them.

## Who the site is for

Recruiters and hiring managers, plus people who might hire him for contract
pipeline or automation work. Design choices that follow from that, and should
be kept when changing the site:

- The first screen answers who he is, what role, how many years, which stack,
  where he is and how to reach him, without scrolling.
- Nothing is hidden behind a script. Scroll-in effects are CSS-only and the
  page is complete without JavaScript.
- Every case study opens with the three-line `brief`, and ends with a contact
  prompt.
- The email address is always shown as text with a copy button, because
  `mailto:` links do nothing on many work computers.
- Section names in the menu are the ones a recruiter looks for: About, Work,
  Experience, Skills, CV, Contact.
- Smallest text on the page is about 12px. Do not go below it.
- Below 1040px wide the diagrams become vertical lists; below 820px the menu
  collapses into a "Menu" button.

## Code map

| File | What it is |
|---|---|
| `build.mjs` | Templates and the build. Also the dev server (`--serve`). |
| `content/` | All text. Edit here for content changes. |
| `src/styles.css` | All styling. Colour and type tokens are at the top; dark mode follows the system setting. |
| `src/main.js` | Hero data stream, stepper tabs, project filter, copy-email button, mobile menu, nav state, cursor glow. The page works without it. Do not name a top-level variable `top`, `name` or `status`: they clash with browser globals and stop the whole script. |
| `public/` | Copied to the site root as-is (CV PDF, favicon, `icons/`, `og.png`). |
| `tools/og.html` | Source of `public/og.png`, the image shown when the link is shared. If the headline or its three numbers change, edit it, open it in a 1200x630 headless Chrome window and screenshot it over `public/og.png`. |
| `dist/` | Build output. Git-ignored; never edit by hand. |

Design: one dark theme, on purpose (there is no light mode). Deep navy canvas,
panels a shade lighter, soft indigo light behind the hero and contact panels,
diagrams on dot-grid "boards". Indigo is for links and data in motion.
**Orange is reserved for the constraint or the thing that broke** (the
highlighted phrase in the headline, the bad rows in the hero stream, hot nodes
in the stepper, evidence numbers in the stories); do not use it for anything
else.

The hero animation is the signature: rows enter as a mess, the orange ones are
dropped at the "validate" gate, the rest are pulled into lanes at "model". It
is drawn on a canvas by `src/main.js`, pauses when off screen, and is a single
still frame for people who ask for reduced motion.

Motion elsewhere: sections ease in as they scroll into view using CSS
scroll-driven animation only, so content is never hidden if a script fails or
the browser does not support it. Cards lift and light up under the cursor. Type is Archivo (headings, set wide), IBM Plex Sans (body)
and IBM Plex Mono (labels, figures, diagrams). All links are relative, so the
site works from any folder on any static host.

## Commands

```
npm run build   # writes dist/
npm run dev     # builds, serves http://localhost:4321, rebuilds on save
```

The preview server keeps its templates in memory: after editing `build.mjs`,
restart `npm run dev`, or it will keep writing pages from the old templates.

`site.url` in `content/site.mjs` is the live address. It is used for the
canonical link and the share image, so update it if the site moves to a custom
domain.

Deploying: any static host. Build command `npm run build`, output folder
`dist`. Not deployed anywhere yet (as of 2026-11-16).
